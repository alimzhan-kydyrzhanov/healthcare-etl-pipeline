## 2. Теория с нуля

### ETL и ELT
- **Extract** — забрать данные из источника (файлы, API, база).
- **Transform** — почистить, привести типы, объединить, посчитать.
- **Load** — положить в хранилище (warehouse), где аналитики будут писать SQL.

**ETL**: трансформируем *до* загрузки (как в этом проекте — pandas в Python).
**ELT**: сначала грузим сырые данные в хранилище, потом трансформируем SQL-ом внутри него
(так делают в Databricks, Snowflake, BigQuery — там много вычислительной мощности).
*Аналогия:* ETL — моешь овощи дома, потом кладёшь в холодильник. ELT — кладёшь всё как есть, моешь потом, когда нужно.

### Data quality (качество данных)
Основные проверки: **completeness** (нет пустых), **validity** (дата — это дата), **uniqueness**
(нет дублей), **referential integrity** (процедура ссылается на существующего пациента).
Плохие строки не выбрасываются молча, а уходят в **карантин** (`dq_rejected`) с причиной — так их
можно исправить в источнике. Ты это знаешь по клинике: ошибка в одной записи ломает всё, что строится на ней дальше.

### Star schema (схема «звезда»)
- **Fact table** (`fact_procedure`) — события, «что произошло»: одна строка = одна процедура, с числами (стоимость).
- **Dimension tables** (`dim_patient`, `dim_procedure`, `dim_date`) — описания «кто / что / когда».
Факт в центре, измерения вокруг — получается звезда. Аналитику так просто писать запросы:
`JOIN` факта с нужными измерениями и `GROUP BY`.
Почему `dim_date` отдельно: чтобы группировать по кварталу или дню недели без вычислений в каждом запросе.

### Pseudonymization и GDPR
Медицинские данные — особая категория по GDPR. Мы:
1. заменяем `patient_id` на хэш **SHA-256 с солью** → один пациент всегда даёт один ключ (JOIN работает), но узнать ID нельзя;
2. **минимизируем данные**: имя и точная дата рождения в хранилище не попадают, только возрастная группа.
Почему соль: без неё можно перебрать все `PT00001…PT99999`, посчитать хэши и сопоставить.
⚠️ Псевдонимизация ≠ анонимизация: с солью данные восстановимы, поэтому по GDPR они всё ещё персональные.

### Идемпотентность и транзакции
**Идемпотентно** = запустил 1 раз или 10 раз — результат одинаковый (нет дублей). У нас это полная перезагрузка (DELETE + INSERT).
**Транзакция** = всё или ничего: если загрузка упала посередине, база откатится и не останется «половинчатой».

### Оконные функции SQL
`RANK() OVER (PARTITION BY age_group ORDER BY COUNT(*) DESC)` — нумерует строки *внутри каждой группы*,
не схлопывая их, как `GROUP BY`. Так находим «топ-1 процедуру в каждой возрастной группе».

### Docker, CI/CD, Git
- **Docker** упаковывает код с зависимостями, и он одинаково запускается везде.
- **CI** (GitHub Actions) при каждом `git push` сам ставит зависимости, гоняет тесты и весь пайплайн. Сломал — сразу видно.
- **Git** — история изменений; работа через ветки и pull request.

### GenAI-шаг
Заметки врачей — свободный текст. LLM (Claude) раскладывает их по категориям. Важные инженерные решения:
ответ проверяется по списку допустимых категорий, при ошибке — откат на правила; `lru_cache` не шлёт одну и ту же заметку дважды (экономия денег);
без ключа API работают правила — тесты и CI не зависят от внешнего сервиса.

## 4. Разбор файлов

- **`generate_data.py`** — синтетические данные с намеренными ошибками (пустое имя, дата `1990-13-45`, дубль, несуществующий пациент, код `X999`, отрицательная цена). *Почему:* реальные медданные использовать нельзя, а ошибки нужны, чтобы проверки было что ловить.
- **`extract.py`** — читает файлы **как есть**, всё как строки (`dtype=str`). *Почему:* extract ничего не исправляет, иначе ошибка спрячется до валидации.
- **`validate.py`** — каждая проверка = маска pandas + причина. *Обрати внимание:* после отбраковки 2 пациентов отбраковываются и их процедуры (`unknown patient_id` = 8: 1 намеренная + 7 «каскадных»). Это правильно: нельзя грузить факт без измерения.
- **`transform.py`** — типы, псевдоним, возрастная группа, `dim_date`. `age_group` учитывает, был ли уже день рождения в этом году.
- **`categorize.py`** — LLM или правила (см. выше).
- **`load.py`** — схема, транзакция, `PRAGMA foreign_keys = ON` (в SQLite внешние ключи по умолчанию выключены!), `to_sql`.
- **`run.py`** — склеивает шаги, пишет логи и строку в `etl_runs` (когда, сколько загружено/отбраковано).
- **`schema.sql`** — `CHECK`-ограничения (cost ≥ 0) — вторая линия защиты на уровне базы; индексы на частые JOIN-колонки.
- **`reports.sql`** — 3 аналитических запроса, достаются по метке `-- name:`.
- **`tests/`** — юнит-тесты функций + интеграционный тест «запуск дважды не дублирует данные».

## 5. Решения и компромиссы

| Решение | Альтернатива | Почему так |
|---|---|---|
| SQLite | PostgreSQL | Запускается без установки; SQL почти тот же. В проде — Postgres / Redshift / Databricks SQL |
| pandas | PySpark | Данных мало. На миллионах строк — Spark (в Databricks), логика шагов та же |
| Полная перезагрузка | Инкрементальная (только новое) | Проще и идемпотентно. Минус — медленно на больших объёмах (см. задание 2) |
| Карантин вместо удаления | Просто dropna() | Ничего не теряется молча, можно исправить источник |
| Правила как fallback для LLM | Только LLM | Надёжность, цена, тестируемость |

## 7. Слабые места и как улучшить

- Полная перезагрузка → **incremental load** по `performed_at` / watermark.
- Нет оркестратора → **Airflow** DAG с расписанием и ретраями.
- Локальные файлы → **AWS S3** как data lake, **AWS Glue** или **Databricks** для обработки, Parquet вместо CSV.
- Нет проверки схемы входа → Pydantic или Great Expectations.
- Соль из переменной окружения → в проде в **secrets manager** (AWS Secrets Manager).
- SCD (изменение данных пациента со временем) не учитывается → SCD Type 2.

**Если спросят про AWS / Databricks** (честно): «Пока не работал в продакшене, изучаю. В этом проекте
`data/raw` — это то, что было бы в S3, `run.py` — то, что был бы job в Glue / Databricks, а pandas я бы заменил на PySpark».

## 9. Вероятные вопросы и ответы

1. **Расскажи о проекте.** — ETL-пайплайн для данных клиники: CSV и JSON → проверки качества → псевдонимизация → star schema в SQLite → аналитические отчёты. Вырос из моего опыта в Ala Clinic, где я вручную проверял записи пациентов.
2. **ETL vs ELT?** — См. раздел 2. Здесь ETL, потому что трансформация в pandas; в облачном хранилище выбрал бы ELT.
3. **Что делаешь с плохими данными?** — Карантин в `dq_rejected` с причиной и run_id; ничего не удаляю молча.
4. **Почему 8 отклонённых процедур, если ты испортил одну?** — Каскад: процедуры отбракованных пациентов не проходят referential integrity.
5. **Что такое fact и dimension?** — Факт — событие с метриками, измерение — контекст. Пример из проекта.
6. **Как защищены персональные данные?** — SHA-256 с солью, минимизация (нет имени и даты рождения). Это псевдонимизация, не анонимизация.
7. **Почему нужна соль?** — Без неё хэши всех возможных ID можно посчитать перебором.
8. **Что если запустить пайплайн дважды?** — Идемпотентно, есть тест.
9. **Что если упадёт посередине загрузки?** — Транзакция, откат.
10. **`GROUP BY` vs оконная функция?** — GROUP BY схлопывает строки, окно — считает по группе, сохраняя строки.
11. **Как масштабировать на 100 млн строк?** — Parquet в S3, PySpark / Databricks, инкрементальная загрузка, партиционирование по дате.
12. **Как запускать каждый день?** — Airflow DAG / cron, ретраи, алерты при падении (по `etl_runs`).
13. **Что делает CI?** — На каждый push: зависимости, pytest, полный прогон пайплайна.
14. **Зачем Docker?** — Одинаковое окружение у меня, в CI и на сервере.
15. **Как использовал GenAI?** — Классификация заметок с валидацией ответа, кэшем и fallback на правила. Плюс пишу код с Claude Code / Cursor, но каждую строку проверяю и понимаю.
16. **Что бы улучшил?** — Раздел 7.
17. **Почему `dtype=str` при чтении CSV?** — Чтобы pandas не «угадывал» типы и не прятал ошибки (например, ID с ведущими нулями).
18. **Зачем `PRAGMA foreign_keys = ON`?** — В SQLite внешние ключи по умолчанию не проверяются.
